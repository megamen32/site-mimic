# Статус мимикрии: что уже совпадает байт-в-байт, а что нет

**Дата: 2026-09-02. Проверено живьём на стенде `fp.example.test`.**

Как проверяем: реальный браузер (Windows 11 Chrome 152 headed, Android 10
Chrome 152, Safari на macOS) заходит на `https://fp.example.test/fp` —
стенд отдаёт полный фингерпринт посетителя: сырое TLS-приветствие
(JA3/JA4/JA4_r/hex), расшифрованные h2-кадры (SETTINGS, порядок
заголовков), HTTP-заголовки, IP TTL и TCP-опции SYN. Затем тот же стенд
посещает наш клиент (site-mimic), и отчёты сравниваются в одном месте
(`/fp/recent` — последние 50 отчётов). h2-кадры дополнительно
расшифрованы из pcaps по TLS-keylog.

## Что уже совпадает с реальным Chrome — байт-в-байт

| HTTP-заголовки, множество имён | 13 | 13 | ✅ совпадает |

| Cookies / заголовки навигации | — | cookie-jar replay в клиенте | ✅ |

## Что разъехалось за сутки — главный урок

**ClientHello Chrome — не константа, а серверный эксперимент.**
2026-09-01 реальный Chrome 152 (Windows headed и «телефон» через
PCAPdroid-MITM) давал 18-расширенный набор с post-quantum-подписями и
`pre_shared_key`+`0xCA34`: JA4 `t13d1518h2_8daaf6152771_e2d80978ab2e`.
2026-09-02 тот же Chrome на тех же машинах даёт **17 расширений**,
`JA4 t13d1517h2_8daaf6152771_cb7bf5808d99` — одинаковый на Linux,
Windows и Android. Google выключил Finch-флаг за ночь. Вывод: эталоны
нужно снимать со стенда автоматически и регулярно, «вчерашний» JA4 не
обязан быть «завтрашним».

Следствия, зафиксированные сегодня:

- `chrome_exact` (транспорт, делегирующий bundled Chromium) отстал:
  его Chromium — 151, на проводе `t13d1516h2_…806a8c22fdea` против
  реального `cb7bf5808d99`. Нужно обновить bundled-браузер — и TLS
  снова байт-в-байт.
- uTLS-спека `chrome_152` собрана под вчерашний 18-расширенный
  эксперимент и сегодня устарела; актуальный эталон — 17 расширений.
- Строка матрицы «Android 152 = 18 расширений» была артефактом
  PCAPdroid-MITM (аддон сам перешифровывает TLS своим клиентом).
  Реальный end-to-end телефонный Chrome 152 = десктопный набор.

Наша мимикрия теперь покрывает обе формы: свежую (chrome_exact / chrome_152) и resumption (cache + chrome_152_psk).

## Что пока НЕ мимикрим (честный список)

1. **TCP SYN, per-connection**: порядок TCP-опций и наличие
   timestamps задаются глобальным sysctl хоста, а не профилем.
   Видно на стенде: Windows шлёт `mss,wscale,sackOK`, наш Linux —
   `mss,sackOK,wscale`. Множество то же, порядок — Linux. Лечится
   отдельным netns с raw-SYN (или eBPF) на профиль.
2. **QUIC/HTTP3, транспортные параметры**: ЗАКРЫТО 2026-09-02 (вечер).
   Реальные 94 байта transport parameters Chrome (ext 0x0039 из capture'а
   телефонного QUIC) смапплены в типизированную структуру
   `TransportParameters` uQUIC — дефолтный hello теперь несёт браузерные
   значения (max_udp 1472, окна 6 MiB / 15 MiB, idle 30000, streams 100/103,
   datagram 64 KiB, google_connection_options "ORIGECCPIW2X", GREASE-пара с
   рандомным ID) при сохранении 11-расширенной формы
   `q13d0311h3_55b375c5d22e_7ae7f4a1bb73` (tshark-verified: форма не
   уезжает в q13d0314h3).
3. ~~**TLS session resumption**~~ ЗАКРЫТО 2026-10-20: клиент возобновляет
   сессию — тикет живёт в общем хранилище, но именован по (идентичность
   профиля, сервер), поэтому тикет не переходит между профилями. Свежие
   приветствия не сдвинулись; возобновлённые формы — захваченные
   `e2d80978ab2e` (chrome_152) и `352634941f3a` (max_app). Открыто:
   `node_24` (нет подтверждённой захватом возобновлённой формы) и
   `firefox_auto`/`ios_auto`.
4. **ECH**: реальный Chrome отправляет Encrypted Client Hello GREASE;
   поведение нашего стека — не разобрано до конца.
5. **IP ID / DF / TOS паттерны** и прочие мелочи L3 — фиксируются
   стендом, но пока не подменяются per-profile.
6. **Поведенческий слой**: тайминги, порядок загрузки ресурсов, кэш,
   referer-цепочки — не мимикрируются транспортом (отдельная работа).
7. **Пользовательские поля**: `accept-language` — параметризован
   (поле `accept_language` профиля); остальные (домашняя страница,
   часовой пояс UI) — по мере надобности.

## Поведенческий слой — отдельная задача (статус и план)

Статус: **ЧАСТИЧНО РЕАЛИЗОВАН** (2026-09-02, вечер) — один запрос больше
не является нормой: профили несут `resource_plan` (навигация → favicon →
XHR с per-type заголовками, referer-цепочками и джиттером задержек), у
`stand-probe` есть выбор профилей по имени из `examples/profiles/`
(windows-chrome152 / android-chrome152 / linux-chrome152; android — из
реального e2e-capture телефона). На проводе: документ шлёт navigate+user,
favicon — image/no-cors/same-origin + referer и БЕЗ навигационных
заголовков, XHR — empty/cors + referer; JA4 стабилен по всей сессии.

Закрыто (шаг 3, 2026-10-06): **кэш-поведение** — `mimic.PageCache`
(сессионный кэш валидаторов ETag/Last-Modified по URL) +
`Profile.RunPlanSession`: первая навигация сохраняет валидаторы ответа,
повторные replay-ят их как `If-None-Match`/`If-Modified-Since` (304
подтверждает запись, 200 обновляет, ответ без валидаторов — сбрасывает, как
браузер). `stand-probe` держит один PageCache на все повторы — вторая
навигация сессии больше не выглядит как первая. Freshness-времена жизни
намеренно не парсим: каждый шаг всё равно выходит на провод, чтобы стенд
видел полную сессию. Проверено тестом
`TestRunPlanSessionConditionalRevalidation` (4 прохода: plain → cond/304 →
последняя ревалидация → plain) и **живьём на стенде**: /fp теперь ссылается
на два статических ассета с валидаторами (/favicon.ico, /fp/dot.png — ETag +
Last-Modified + must-revalidate, 304 по If-None-Match), и /fp/recent
показывает условные запросы ОБЕИХ сторон рядом — реальный Chrome на
hand-off-вкладке и наш PageCache шлют идентичный
`If-None-Match: "fpd-pixel-v1"` на /fp/dot.png. Нюанс: Chrome не
ревалидирует favicon на повторных навигациях (отдельная favicon-DB), наш
PageCache — HTTP-семантика, ревалидирует; на /fp/dot.png (обычный <img>)
поведение совпадает точно.

Оставшиеся шаги:
4. **Тайминги**: автоматизирована «подмешивающая» половина —
   `tools/har_to_plan.py` превращает экспорт DevTools-HAR (живая запись
   целевого сайта руками оператора, без автоматизации на проводе) в готовый
   resource_plan: измеренные паузы между стартами запросов как
   delay_min/max_ms (±20% джиттера), referer-цепочки, методы, кросс-доменные
   URL абсолютами; 304-ревалидации выбрасываются (их повторяет PageCache из
   шага 3). Сам HAR-съём остаётся ручным действием оператора на целевом
   сайте (DevTools → Network → Export HAR) — по требованию «не по CDP».
5. **Наборы заголовков по типу ресурса**: расширять типы (style/script/font
   уже есть базовые) по потребности целевого сайта.

Оценка: п.4 закрыт инструментально, съём HAR — по появлению целевого сайта;
п.5 — по потребности конкретного целевого сайта.

## Прогресс 2026-10-12 — Mac mini (macOS) паритет, LAN-стенд

Реальный Chrome 153.0.8010.36 на Mac mini (macOS 15.7.8) против нашего
`chrome_exact`+`mac-chrome153` на LAN-стенде (fpd на 192.0.2.100:31777,
прямо, без haproxy — fpd теперь принимает соединения и без PPv2, сниффер
настраивается `-sport`):

- **JA4**: свежая форма реального браузера
  `t13i1516h2_8daaf6152771_cb7bf5808d99` воспроизведена байт-в-байт на
  каждом нашем соединении; JA3 у обеих сторон шуффлится от соединения к
  соединению (пер-коннектная случайность — норма).
- **Заголовки**: набор (13 имён, zstd, `Priority: u=0, i`) и проводной
  порядок навигационного запроса идентичны символ-в-символ (расшифровка
  keylog+tshark): `:method,:authority,:scheme,:path,sec-ch-ua,…,priority`.
- **HTTP/2**: клиентские SETTINGS — значения, набор и порядок полей
  (`65536/0/6291456/262144`) и коннектный WINDOW_UPDATE `15663105`
  идентичны.
- **L3/L4**: TTL 64, DF, IP ID 0, SYN `mss 1460,nop,wscale 6,nop,nop,TS`,
  win 65535 — нативный macOS-стек, одинаковый у реального Chrome (все 4
  режима) и у нашего клиента; ничего не подменялось.
- **UA-токен**: headed `Chrome/153.0.0.0` vs headless `HeadlessChrome/153.0.0.0`
  — единственное отличие режимов реального браузера; наш клиент шлёт
  профильный UA (в headless-подобном использовании токен остаётся Chrome —
  учтено при конструировании легенды).
- **Разрыв**: resumption-форма реального Chrome
  (`t13i1517h2_…e2d80978ab2e`, PSK) нашим стеком не воспроизводится:
  `headless-client.Transport()` создаёт свежий session cache на каждый
  вызов, resumption-hello не возникает. Ранее задокументированное
  «chrome_exact возобновляет через upstream sessionCache» сегодня не
  подтвердилось — апстрим-пункт.

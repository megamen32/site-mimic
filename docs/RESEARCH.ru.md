# Исследование простыми словами: как мы делали Go-клиент неотличимым от браузера

Дата: 2026-09-02. Всё из этой статьи измерено на реальных устройствах и
проверено на проводе (tcpdump), а не взято из документации. Технические
детали и точные значения — в [fingerprint-matrix.md](fingerprint-matrix.md),
[phone-reference.md](phone-reference.md) и [methodology.md](methodology.md).

## Зачем всё это

Обычный Go-клиент палится сайтом за секунду: у него уникальный «почерк» на
каждом уровне сети. Мы учим Go-программу притворяться настоящим браузером —
с телефона, с Windows, с Linux.

## Маленький словарик

- **ClientHello** — первое сообщение браузера при установке TLS-соединения
  («здравствуйте, я умею вот это»). Содержит списки шифров и расширений.
  Это главный «паспорт» клиента.
- **JA3** — старый отпечаток: MD5-хеш всего ClientHello в порядке появления.
  Chrome специально перемешивает расширения в каждом соединении, поэтому
  JA3 у настоящего Chrome **меняется при каждом подключении**. Стабильный
  JA3 — сам по себе подозрителен.
- **JA4** — новый отпечаток (FoxIO): устойчив к перемешиванию, потому что
  списки сортируются перед хешированием. Выглядит как
  `t13d1516h2_8daaf6152771_e2d80978ab2e`: «TCP, TLS 1.3, есть домен,
  15 шифров, 16 расширений, говорю по h2» + два коротких хеша от наборов.
  Меняется только когда у браузера реально меняются возможности (например,
  вышла новая версия).
- **TTL** — счётчик в каждом IP-пакете. Его ставит ядро: Windows = 128,
  Linux/Android = 64. Каждый роутер уменьшает на 1. Поэтому сайт с первого
  пакета видит семейство твоей ОС.
- **WFP** (Windows Filtering Platform) — официальная «точка встраивания» в
  сетевой стек Windows. AdGuard в режиме WFP встроен драйвером: он смотрит
  и режет пакеты, но НЕ переписывает их. Поэтому с включённым AdGuard
  ClientHello Chrome дошёл до провода нетронутым — мы это проверили A/B-тестом.
- **Hairpin NAT** — когда ты заходишь с домашней машины на свой же
  публичный адрес: роутер «разворачивает» пакет обратно в локалку,
  подменяя адрес отправителя на свой. Из-за этого наши первые захваты
  Windows «не видели» трафик — он приходил с адреса роутера.

## Что мы измерили (матрица, кратко)

| Устройство | Браузер | JA4 | TTL |
|---|---|---|---|
| Телефон Android (S21 Ultra) | Chrome 149 | `t13d1516h2_8daaf6152771_d8a2da3f94cd` | 64 |
| Тот же телефон после обновления | Chrome 152 | `t13d1518h2_8daaf6152771_e2d80978ab2e` | 64 |
| Linux-компьютер | Chrome 152 | `t13d1517h2_8daaf6152771_cb7bf5808d99` | 64 |
| Windows 11 | Chrome 151 (AdGuard ВКЛ) | `t13d1516h2_8daaf6152771_806a8c22fdea` | **128** |
| Windows 11 | Chrome 152 (AdGuard ВЫКЛ) | `t13d1518h2_8daaf6152771_e2d80978ab2e` | **128** |
| Windows 11 | curl (родной TLS Windows) | `t13i2511h1_f5a23f7cfd7b_36bf25f296df` | 128 |
| Windows 11 | BrowserOS (Chromium 148) | `t13d1813h1_85036bcba153_d339722ba4af` | 64 |

Выводы, которые важнее цифр:

1. **Chrome 152 добавил постквантовые подписи** (ML-DSA) и новое
   расширение 0xCA24 — поэтому JA4 сдвинулся на всех платформах.
2. **На версиях 152 отпечаток зависит от платформы**: у Windows и Android
   18 расширений, у Linux — 17. Нельзя снять эталон на одной ОС и
   подставить на другую.
3. **AdGuard не меняет ни ClientHello, ни заголовки** (режим WFP) — A/B
   тест с ним и без него показал одинаковые структуры.
4. **Headless-браузер = headed-браузер** на уровне сети: различие только в
   слове `Headless` внутри User-Agent.
5. **По http (незащищённый контекст) Chrome не шлёт client hints и не
   просит brotli/zstd** — снимать эталоны можно только по https.
6. **BrowserOS — не «ещё один Chrome»**: у него только h1, другие шифры,
   меньше расширений. Любая JA4-проверка отличит его мгновенно.

## Что мы уже умеем мимикрировать (готово, проверено на проводе)

| Слой | Как | Статус |
|---|---|---|
| TLS ClientHello (JA4/JA3) | uTLS-спеки: `chrome_exact` (точная копия), `android_149` (телефон), `chrome_auto` | ✅ каждый эталон воспроизведён нашими инструментами |
| Перемешивание расширений | есть и у нас: JA3 меняется каждое соединение, JA4 стабилен — как у настоящего Chrome | ✅ |
| TTL («Windows это 128») | `WithTTL(128)` или `"ip_ttl": 128` в профиле | ✅ tcpdump подтверждает |
| Заголовки (состав и порядок) | профили из реальных захватов: `vk-ru` (Linux 152), `vk-ru-mobile` (Android), `vk-ru-windows` (Windows) | ✅ |
| Порядок заголовков на проводе + HTTP/2 фреймы | делегирование headless-client (режим `chrome_exact`) | ✅ |
| Cookies из настоящего браузера | `LoadCookieJarFile` + `-cookies` | ✅ |
| Прокси без потери фингерпринта | CONNECT-туннель руками до TLS | ✅ |

## Чего мы пока НЕ мимикрируем (план работ, по порядку ценности)

1. **Chrome 152-спека (PQ + 0xCA24).** Текущие транспорты дают набор 149
   (без постквантовых подписей). Эталоны 152 сняты для всех платформ —
   нужен кастомный ClientHelloSpec: убрать/добавить 3 сигнатуры
   0x0904-0906 и расширение 0xCA24. Сложность: средняя, всё для проверки
   есть. **Это следующий логичный шаг.**
2. **TCP-опции кроме TTL** (у Windows нет timestamps, wscale 8 вместо 7).
   Ставятся sysctl на хосте (`net.ipv4.tcp_timestamps=0` и буферы) —
   дёшево, но влияет на всю машину; per-socket — только raw sockets.
3. **QUIC / HTTP3.** Часть мобильного трафика ходит по h3 (мы видели в
   захвате), мы говорим только по TCP. Редко гейтится, но след есть.
   Сложность: высокая (отдельный QUIC-стек).
4. **Платформенные нюанси 152**: Windows/Android = 18 расширений,
   Linux = 17 — при кастомной спеке из п.1 учесть целевую платформу.
5. **Поведение и JavaScript** — осознанно вне скоупа. Против JS-челленджей
   (типа wbaas у Wildberries) транспорт не поможет: нужен настоящий
   браузер + перенос кук (мы умеем). Это не «не умеем», это другая задача.
6. **Поведенческий анализ** — настоящий браузер делает десятки соединений
   (favicon, preconnect, фоновые сервисы), наш клиент — одна навигация.
   Против поведенческих анти-ботов это видно; лечится сценарием, а не
   транспортом.

## Как это всё воспроизвести

```sh
# эталоны с провода из любого pcap:
python3 tools/ja4_from_pcap.py captures/файл.pcap
# QUIC-приветствия (требует cryptography):
python3 tools/ja4_from_pcap.py захват_с_quic.pcap
# наш клиент как Windows:
cd examples/vk-ru-windows && go run .        # в профиле ip_ttl: 128
# наш клиент как Android:
cd examples/vk-ru-mobile && go run .
# проверка JA4 своего дампа:
go run . -dump ch.json && python3 ../../tools/parse_clienthello.py ch.json
```

Инструменты: `tools/ja3_ja4.py` (JA3 + JA4 по спецификации FoxIO),
`tools/ja4_from_pcap.py` (извлечение hello из pcap, включая битые
PCAPdroid-захваты), `tools/quic_initial.py` (расшифровка QUIC Initial).
